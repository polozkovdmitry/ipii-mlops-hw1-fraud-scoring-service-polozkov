# Скоринг фродовых транзакций из Kafka

_NB! ниже написано с помощью ИИ, но я перепроверял и по максимому убирал неестественность языка. Надеюсь не слишком вырвиглазно получилось_

Сервис скоринга транзакций на основе семинарского проекта mts25_mlops_hw2_real_time_fraud_detection. Транзакции в формате test.csv из соревнования teta-ml-1-2025 читаются из топика Kafka transactions, проходят препроцессинг, скорятся моделью на CPU, и результат пишется в топик scores в формате (transaction_id, score, fraud_flag). Отдельный сервис score_writer читает этот топик и складывает результаты в Postgres, а в интерфейсе по кнопке «Посмотреть результаты» можно увидеть последние фродовые транзакции и гистограмму скоров.

Модель в сервисе теперь не CatBoost, как на семинаре, а логистическая регрессия, и её можно переобучить прямо из интерфейса с другими гиперпараметрами и порогом (подробнее в разделе «Переобучаемая модель» ниже). CatBoost я не выкинул, а отложил: его код лежит рядом в файлах preprocessing_catboost.py и scorer_catboost.py, на случай если к нему понадобится вернуться.

# Запуск

Требования: Docker 20.10+ и Docker Compose v2, а также свободные порты 8080, 8501, 8000, 9095 и 2181. Для переобучения модели нужен файл data/train.csv, подробнее в разделе про переобучение ниже (без него сервис всё равно стартует и скорит базовой моделью, не работает только кнопка переобучения). Postgres наружу не публикуется, он доступен только внутри docker-сети ml-scorer.

    git clone https://github.com/polozkovdmitry/ipii-mlops-hw1-fraud-scoring-service-polozkov.git
    cd ipii-mlops-hw1-fraud-scoring-service-polozkov
    docker compose up --build


Далее открываем http://localhost:8501, загрузить CSV в формате test.csv и нажать «Отправить». Для проверки лежат два примера, оба взяты из test.csv: misc/test_20.csv (первые 20 строк, для быстрой проверки) и misc/test_382.csv (382 строки, пачка среднего размера). Лучше брать небольшие файлы, на полном test.csv обработка идёт долго. Результаты видны в Kafka UI на http://localhost:8080, в топике scores, а также в самом интерфейсе: ниже на странице есть раздел «Результаты скоринга», по кнопке «Посмотреть результаты» показываются 10 последних транзакций, у которых score выше текущего порога, и гистограмма скоров. Гистограмму можно строить либо по последним 100 транзакциям, либо по всей последней отправленной пачке (последнюю пачку интерфейс помнит, пока страница не перезагружена). Скоры появляются в базе не мгновенно, поэтому если сразу после отправки результатов нет, нужно чуть подождать и нажать кнопку ещё раз.

Без интерфейса данные можно отправить скриптом: python scripts/send_sample.py misc/test_20.csv (нужны kafka-python и pandas). Логи сервисов: `docker compose logs -f fraud_detector` и `docker compose logs -f score_writer`. Остановка: `docker compose down` (накопленные в Postgres результаты при этом сохраняются, чтобы удалить и их, нужно `docker compose down -v`).

# Отличия от семинарского кода и улучшения

1. Не нужен train.csv для препроцессинга CatBoost. На семинаре при каждом старте контейнера читался весь train.csv (145 МБ), только чтобы получить таблицы кодирования категорий. В GitHub такой файл не залить (лимит 100 МБ), к тому же старт был медленным. Теперь эти статистики посчитаны один раз скриптом scripts/build_artifacts.py и лежат в fraud_detector/artifacts/preproc_artifacts.pkl (64 КБ). Результат препроцессинга я сверил со старым кодом на всём test.csv, признаки совпадают полностью. Для логрега эти артефакты уже не нужны, всё нужное лежит внутри самой модели, но для CatBoost-версии они остались.
2. Препроцессинг теперь работает с пачкой строк и использует готовые словари из артефактов. Раньше на каждое сообщение заново делались merge с train данными и обсчёт имьютера.
3. Kafka теперь умеет читать пачками (до 100 сообщений), скоринг и flush делаются один раз на пачку, а не на каждое сообщение. Если пачка падает, её обрабатываем по одной строке, чтобы одна плохая запись не ломала остальные; невалидный JSON просто пропускается с записью в лог.
4. Выходное сообщение теперь один JSON-объект, а не массив из одного объекта, как было из-за to_json(orient='records'). Так сообщение соответствует формату из задания (три поля) и любой потребитель топика может читать его напрямую, без распаковки списка. Топик называется scores, как в задании, чтобы название не расходилось с требованиями. На вход, кроме формата {"transaction_id": ..., "data": {...}} от интерфейса, принимается и просто строка test.csv, тогда id генерируется. Это нужно, чтобы сервис можно было проверить, отправив в топик строку из test.csv любым способом, не только через наш интерфейс.
5. Порог фрода теперь меняется из интерфейса (слайдер в разделе «Модель»), а начальное значение для базовой модели задаётся переменной окружения FRAUD_THRESHOLD в docker-compose.yaml, по умолчанию 0.5. Порог из соревнования был 0.98, но на логреге с class_weight=balanced скоры устроены иначе, поэтому переносить его не стоило.
6. Код скоринга модифицирован, что predict_proba вызывается один раз вместо двух, и убран print на каждое сообщение.
7. В docker-compose сервисы теперь стартуют после того, как Kafka реально готова (healthcheck), а не просто после запуска контейнера, а образ kafka-ui закреплён на версии вместо latest.

# Postgres, score_writer и раздел результатов в интерфейсе

Вместе с остальными контейнерами поднимается база Postgres, в которой автоматически создаётся таблица для хранения результатов: идентификатор транзакции, скор, флаг фрода и время записи. Отдельный сервис score_writer читает топик scores и складывает каждый результат в эту таблицу, так что результаты скоринга можно смотреть не только в Kafka, но и в базе. Повторно доставленные сообщения дублей не создают.

Раздел «Результаты скоринга» в интерфейсе берёт данные из этой же базы: по кнопке «Посмотреть результаты» показывает сначала таблицу последних 10 транзакций, у которых score выше текущего порога, а под ней гистограмму скоров (по последним 100 транзакциям или по последней отправленной пачке, режим выбирается под таблицей).

Тут есть нюанс. fraud_flag в Postgres и в Kafka считается в момент скоринга, и потом уже не меняется. Если бы таблица брала фродовые транзакции по этому флагу, то после смены порога она оставалась бы прежней, и казалось бы, что порог ничего не делает. Поэтому таблица смотрит не на сохранённый флаг, а на сам score и текущий порог, и обновляется сразу. Колонка fraud_flag в ней показывает то решение, которое было принято при скоринге, так что она может не совпадать с текущим порогом, это нормально.

# Переобучаемая модель

Идея в том, чтобы по умолчанию сервис работал на фиксированной базовой модели, а по кнопке в интерфейсе её можно было переобучить с другими параметрами и при этом не сломать то, что уже работает.

**Модель и препроцессинг.** Вместо CatBoost теперь логистическая регрессия из sklearn. Для неё я переписал препроцессинг (fraud_detector/src/preprocessing.py): категории кодируются one-hot, время превращается в синусы и косинусы (час, день недели, месяц), сумма и население берутся в логарифме, расстояние до магазина считается по формуле гаверсинусов. Всё это вместе с масштабированием и самой регрессией собрано в один sklearn Pipeline, поэтому для скоринга достаточно одного файла модели, отдельных артефактов с таблицами кодирования больше нет.

**Базовая модель.** Это файл fraud_detector/models/baseline.joblib (около 40 КБ), он лежит в git. Параметры у него фиксированные (C=1, class_weight=balanced, max_iter=1000, они же стоят по умолчанию в форме переобучения). При самом первом старте сервис регистрирует её в Postgres как дефолтную и делает активной. Пересобрать её можно командой `python fraud_detector/src/trainer.py --data data/train.csv --out fraud_detector/models/baseline.joblib` (версии библиотек как в fraud_detector/requirements.txt).

**Откуда берутся данные для обучения.** train.csv слишком большой для git, поэтому его нужно положить в папку data/ (см. data/README.md), она в .gitignore. В контейнер fraud_detector эта папка монтируется только для чтения (`./data:/data:ro`), то есть сервис может читать файл, но не может его изменить. Чтобы потом дообучать модель на новых данных, например раз в месяц, достаточно заменить файл в этой папке.

**Что есть в интерфейсе.** Внизу страницы раздел «Модель»: активная модель и её метрики (ROC-AUC, PR-AUC, лучший F1 и порог, при котором он достигается; считаются на отложенных 20% train.csv), слайдер порога, форма переобучения (C, class_weight, max_iter), история всех моделей и кнопка «Сбросить на дефолтную модель». Выбор того, на скольких последних примерах обучаться (100, 1000, 10к, 50к), пока заглушка, сейчас обучение идёт на всём train.csv. Обучение занимает несколько секунд, после него новая модель сразу становится активной.

**Порог.** Порог хранится вместе с моделью. Новая переобученная модель получает текущий порог, а при переключении на другую модель из истории действует её собственный порог. Это стоит держать в голове: у модели с class_weight=none скоры гораздо ниже, чем у balanced, и при том же пороге она может почти ничего не помечать, в этом помогает подсказка с порогом лучшего F1.

**История моделей.** Все модели (параметры, метрики, порог, время создания, какая активна) записываются в таблицу models в Postgres. Сами файлы моделей, обученных из интерфейса, лежат в docker-томе trained_models, так что переживают перезапуск контейнеров. Любую модель из истории можно сделать активной обратно.

**Как это устроено внутри.** Обучение и скоринг живут в одном сервисе fraud_detector, отдельного сервиса под обучение я не заводил, чтобы не усложнять. Чтобы обучение не останавливало чтение из Kafka, в сервисе работают два потока: Kafka-цикл остаётся в основном потоке, а в соседнем крутится маленький веб-сервер на FastAPI (порт 8000, интерактивная документация на http://localhost:8000/docs). Интерфейс по HTTP просит его переобучить модель, сменить порог или переключить модель. Активная модель при этом подменяется между пачками сообщений, а не посреди пачки, так что скоринг не прерывается.
